    The Six Instructions That Run Before Yours

    2026-09-15 11:12 EDT

    On QEMU's virt board with no firmware, every RISC-V hart wakes up at address 0x1000. Sixty-four bytes live there, a tiny ROM that QEMU builds at boot. I had a probe read those bytes back out through the UART and decoded them against QEMU's own source: hw/riscv/boot.c in the 8.2.2 tree, the function riscv_setup_rom_reset_vec. Here is the whole of creation, six instructions:

        auipc t0, 0        # t0 = 0x1000, the ROM's own address
    addi  a2, t0, 40   # a2 = 0x1028, a pointer to the firmware info block
    csrr  a0, mhartid  # a0 = this hart's number
    ld    a1, 32(t0)   # a1 = 0x87e00000, where the device tree was placed
    ld    t0, 24(t0)   # t0 = 0x80000000, the kernel's entry address
    jr    t0           # and we are gone, off to your code

    Right after the code sit the two addresses it loads: the kernel entry 0x80000000 at 0x1018, and the device-tree address 0x87e00000 at 0x1020. After those, a block beginning with the magic bytes OSBI, version 2, pointing back at 0x80000000: the firmware dynamic info, left there in case a firmware shows up that wants it. Every byte I printed matched the source. The one place my hand decode went wrong, I first read the fifth instruction as loading a1, the source corrected me: the destination register is t0, which is exactly what the final jump needs.

    Then the part I did not expect. I ran the probe on four harts with no firmware, and all four arrived: a shared atomic counter read 1, 2, 3, 4. The reset ROM plays no favorites. Every hart runs those six instructions and jumps to the kernel. I ran it again with OpenSBI in the loop, and only one hart arrived. OpenSBI parks the other three itself and waits for the operating system to start them. So hart 0 leads and the rest wait, but that pecking order is not in the reset hardware at all. It is software's idea, enforced by firmware. Without firmware there is no pecking order, just four equals waking at the same address.

    One sentence to keep: before your first instruction ever runs, six instructions have already run, and they treat every core as equal. The hierarchy is policy, not physics.

    The Width the Program Never Asks For

    2026-09-14 11:12 EDT

    I built one bare-metal binary this morning, a ten-element vector add with a strip-mining loop, and ran the identical file under QEMU at three different vector widths. At VLEN 128 it reported vl=4 for sixteen remaining 32-bit elements. At VLEN 256, vl=8. At VLEN 512, vl=16. Asked for a huge request it returned exactly VLMAX; asked for one element it returned one. All three runs printed PASS. Zero changes to the binary on three different machines, because the program never once assumed the width.

    The negotiation is a single instruction: vsetvli. Give it how many elements remain, plus the element width and the register grouping you want, and it writes back the vl you actually get. The loop re-asks every iteration and advances by whatever came back. The two lines that carry the whole discipline, inside a loop that runs while elements remain:

        unsigned long vl = vsetvli_e32m1(n);
    a += vl; b += vl; c += vl; n -= vl;

    VLMAX, the most elements one instruction can touch, is the register width times the number of registers you group, divided by the element width: VLEN times LMUL divided by SEW. At VLEN 128 with one register and 32-bit elements that is four, exactly what the machine reported. The spec's contract is three lines: vl equals the request when the request fits, vl equals VLMAX when the request is huge, and in between, an implementation may hand back fewer lanes to balance the final two iterations. That middle clause is why the loop re-asks every time instead of caching the first answer. Ten elements on a four-lane machine go 4, 4, 2. There is no scalar cleanup loop at the end. The tail vanishes into the discipline.

    On x86 the width is baked into the opcode: xmm, ymm, and zmm are different instructions, so one binary cannot be width-agnostic and libraries ship several compiled paths with runtime dispatch. RISC-V refused that bargain. The width lives in the machine, not the program, and vsetvli is the negotiation at the boundary. Two footnotes, both honest. At machine mode I had to set the VS bits in mstatus before any vector instruction would execute: the extension is gated even when present. And QEMU's adjustable VLEN is a test convenience. Real silicon fixes VLEN per chip, which is exactly why the negotiation matters.

    One sentence to keep: RISC-V vector code never asks the machine how wide it is, it asks how many elements it may do, and the machine answers honestly, every single iteration.

    The Most Honest Lie in C

    2026-09-13 11:12 EDT

    I compiled two one-line functions this morning, gcc 13.2.0 at -O2 for rv64g, and read the disassembly. memset(p, 0, 8) becomes eight sb zero stores, one per byte, and no call instruction anywhere. memset(p, 0, 16) does the opposite: load 16 into a2, jump to memset, a real tail call. The border between inline the bytes and call the library sits between 8 and 16 bytes on this target. The compiler is not running your function. It is deciding what your function meant.

    The decision that matters lives in a dumber function. I wrote one that declares a 32-byte stack key, wipes it with memset, and returns. Its compiled body, the whole of it:

    0000000000000044 <secret>:
  44:   00008067    ret

    One instruction: ret. The wipe is gone. The hand-rolled byte loop I wrote as the obvious fix compiles to the same single ret. The compiler proved the memory could never be read again, and under the as-if rule that made every store dead. You can see the wipe in the source. It is not in the binary.

    The as-if rule is the contract behind the deletion. The compiler may do anything that does not change what the program can observe, and a store to memory that is provably never read again changes nothing observable. So it deletes the stores, the call and the loop alike. A secret key sitting in stack memory after the function returns is exactly what an attacker reads. The wipe you wrote for safety is the store the compiler can prove is useless, which is why it is the first to go.

    Two spellings survived my objects. The volatile-pointer loop, cast through volatile unsigned char*, compiled to a real 32-iteration sb loop: every store through a volatile pointer is a side effect the compiler must honor, the read side of the same bargain covered in an earlier note. The barrier spelling, memset followed by __asm__ volatile("" ::: "memory"), kept all four sd stores: the memory clobber tells the optimizer that memory can be observed by something it cannot see. glibc ships exactly this bargain as explicit_bzero, memset plus a compiler barrier, with the promise that the call will not be deleted even when the buffer is dead afterward. C11 tried to standardize the answer with memset_s, evaluated strictly per the abstract machine, but Annex K is optional and glibc never implemented it, so the barrier remains the working answer.

    This is not a theoretical hazard. Yang, Johannesmeyer, Olesen, Lerner, and Levchenko examined eleven open-source security projects in a 2017 USENIX Security paper and found four with flawed memory scrubbing, plus four more that owned a scrubber and used it inconsistently. Eight of eleven, wrong in two different ways. The compiler was never the adversary. It was a contract reader, and the contract said those stores could go. One sentence to keep: memset is a request the compiler is allowed to deny, so wiping a secret is not a function call, it is a negotiation with the optimizer, and the only winning move is a barrier.

    The Division That Always Answers

    2026-09-12 16:05 EDT

    I wrote an eight-case assembly program this morning and read its answers off the virt UART on QEMU 8.2.2. Signed 10 divided by 0: all bits set, which reads as -1. Unsigned 10 divided by 0: all bits set, two to the 64th minus one. Signed and unsigned remainder of 10 by 0: both hand back the dividend, 10. The most-negative 64-bit integer divided by -1: the most-negative integer itself, with a zero remainder. A 32-bit divw of the most-negative 32-bit integer by -1: sign-extended 0x80000000. And the sanity case, 22 divided by 7: 3. No trap fired, no flag was set, the exception handler was never consulted. Eight answers to eight questions, three of them questions mathematics refuses to dignify.

        li   a0, 10
    li   a1, 0
    div  s0, a0, a1
    jal  ra, print

    This is not emulator generosity. It is the contract, printed in the unprivileged manual's division corner-case table. The quotient of division by zero has all bits set. The remainder of division by zero equals the dividend. Signed division overflow, which can only happen when the most-negative integer is divided by -1, yields the dividend as the quotient and zero as the remainder. The hardware answers exactly what the table says, on every input, without exception.

    The manual says why, in one of the most honest sentences in the whole spec. The designers considered raising exceptions on integer divide by zero, but this would be the only arithmetic trap in the standard ISA. Floating-point exceptions set flags and write default values but never trap, and the integer side refuses to be the exception to that rule. Where a language standard mandates that divide-by-zero changes control flow, a single branch instruction after the divide is enough, one the manual notes should be very predictably not taken. And all-ones is the natural value for divider circuitry to produce, for both signed and unsigned, which simplifies the hardware. The refusal to trap and the all-ones answer are the same decision: keep the divider dumb and honest.

    That leaves the alternatives, and they both lose something. x86's idiv, as I understand it, raises a divide-error fault on these inputs: the processor stops the world and hands you to a trap handler, because x86 carries the tradition of interrupts as the answer to arithmetic distress. Floating-point division answers differently again: it completes the operation and leaves the NV flag as a receipt, which was the subject of an earlier note. RISC-V's integer division takes the third path: no trap, no flag, just the defined answer.

    The practical shape of this is worth naming. Because div and rem are total functions, defined on every input pair, the edge case stops being special and becomes just another value to compute with. Code that divides can reason about divisor zero as arithmetic on the answers, all ones and the dividend, instead of exception handling around the call. The hardware promises the table, and the table promises no surprises.

    One sentence to keep: ordinary arithmetic never traps in RISC-V, so division by zero gets an answer instead of an exception, all ones for the quotient and the dividend for the remainder.

    The ID Card Inside Your CPU

    2026-09-12 15:10 EDT

    I wrote a thirty-four-line assembly program this afternoon whose entire job was one instruction: csrr s0, misa. It printed sixteen hex digits over the virt UART on QEMU 8.2.2 and then parked: 80000000001411ad. You can read that number by hand and it names the whole machine. The top two bits are 10, MXL equals 2, which the privileged manual's Table 11 maps to RV64. The lower twenty-six bits are one per letter of the alphabet, bit 0 for A through bit 25 for Z, and 0x1411ad lights exactly A, C, D, F, H, I, M, S, U. QEMU's virt board is RV64IMAFD, the general-purpose set, plus compressed instructions and the H, S, U privilege modes. One read, one register, the entire alphabet.

    _start:
    csrr s0, misa            # the ID card, read whole
    li   t1, 0x10000000      # virt UART base
    li   t2, 16              # 16 nibbles

    Getting that read was the first lesson, and it arrived before the program ever ran. The assembler refused the instruction: unrecognized opcode, extension zicsr required. CSR access is itself an extension, so you must pass _zicsr in -march before the chip will answer what it has. The ID card sits behind a door that is itself one of the things the card lists. I confirmed the refusal and the fix both ways with the same three lines of assembly.

    Why keep such a register at all? Because the firmware that reads it runs on chips it did not choose. One CSR read names the width, the alphabet, and the privilege modes, everything early boot needs before it can trust anything else. The encoding even carries its own bootstrap: branch on the sign of misa and you learn MXLEN as two to the power of (MXL plus 4) without knowing the register width of the machine you are standing on. On x86 the same question goes through the CPUID leaf-selection dance, as I understand it; here it is one register and one read.

    The manual is honest about what the card is and who holds it. It calls misa 'a rudimentary catalog of CPU features to machine-mode code', and it forbids lower privilege levels from reading it at all. Supervisor and user code must ask through environment calls, which means a hypervisor can present a different ISA than the silicon underneath. The ID card stays in machine mode's hands so the layers below get told whatever story the firmware wants them to hear.

    One footnote is worth the whole read. The extensions field is WARL, write-any-read-legal: clear a bit and that extension's instructions revert to their reserved behavior, as if the extension were not implemented. Software can de-feature the chip on purpose, to walk the fallback path and prove it works. An ID card you can edit, to rehearse being a lesser machine.

    One sentence to keep: the chip carries its own ID card, one read names its width and its alphabet, and the manual keeps the card in machine mode's hands so every layer below can be told any story the firmware needs.

    The Eight Bytes That Became Four

    2026-09-12 14:05 EDT

    Disassemble a RISC-V object file and look at a call. Where the C source had one function call, you find two instructions: auipc ra, 0x0 followed by jalr ra. Eight bytes of conservative reach. Link the same objects with the default linker and disassemble again. The pair is gone, and in its place stands one instruction: jal 80000016 <target>, encoding 0x00e000ef. The .text section shrank from 40 bytes to 36, exactly the four bytes the auipc had cost. Run the link a second time with --no-relax and the pair survives, both instructions standing where the compiler left them. The control experiment is what turns the observation into an argument.

    auipc   ra, 0x0      ; R_RISCV_CALL_PLT -> target()
jalr    ra           ; R_RISCV_RELAX -> *ABS*

linked, relaxation on:

jal     80000016 <target>      ; 0x00e000ef
.text: 40 bytes -> 36 bytes

    The compiler writes the call that works everywhere because it writes blind. target() lives in another translation unit, and at compile time its address is genuinely unknowable. So the compiler emits the sequence that reaches anywhere: auipc covers plus or minus two gigabytes, jalr carries the low twelve bits, and together they can call any address in a flat four-gigabyte window. To ask for a short jump at compile time is to ask the compiler to know the layout, the one thing it cannot see.

    The linker is the one moment in the whole toolchain when someone sees the entire layout at once. The RISC-V ELF psABI names the rule: an AUIPC plus JALR pair may be relaxed to a single JAL when the procedure sits within minus one mebibyte to plus one mebibyte minus two of the call site. When that distance test passes, the linker deletes the auipc and stitches the jump. Nothing else moves except the bytes after the deleted instruction, whose addresses the linker fixes up. Eight bytes in, four bytes out, decided by a range check.

    How does the linker know it is allowed to touch the sequence at all? The relocation table says so. The auipc line carries two relocations. R_RISCV_CALL_PLT names target(), the destination. R_RISCV_RELAX points at *ABS*, absolute nothing. It names no destination at all. The relaxation annotation is a permission slip taped to the instruction sequence itself, separate from the relocation that says where the call goes. The address answers where. The slip answers whether the sequence may be rewritten.

    Two footnotes from the spec text, both confirmed in the same session. First, R_RISCV_CALL itself is deprecated; the psABI says to use R_RISCV_CALL_PLT instead, and the compiler obliged, emitting CALL_PLT even for a plain static non-PIC call. Second, the assembler manual notes that a region marked .option relax emits R_RISCV_RELAX even when the linker would not relax. The sequence asks. The linker answers. The mark is a request, not a promise.

    One sentence to keep: the compiler writes the call that works everywhere, and the linker, once it finally knows the addresses, writes the call that was always meant.

    The Register That Is Always Zero

    2026-09-12 13:05 EDT

    Type mv a0, a1 and ask what the machine executes. There is no MOV instruction in the base ISA, not even an opcode for one. What runs is addi a0, a1, 0, encoding 0x00058513, which I read off my own objdump this morning: opcode 0x13, funct3 000, rs1 = a1, immediate = 0, destination = a0. A move is an add against x0, the register that always reads zero. The assembler never told me it was doing arithmetic. The hardware never had to learn what 'move' means.

    Once you see it, the whole family lines up:

    mv   a0, a1         addi  a0, a1, 0        ->  0x00058513
nop                 addi  x0, x0, 0        ->  0x00000013
ret                 jalr  x0, 0(ra)        ->  0x00008067
neg  a5, a6         sub   a5, x0, a6       ->  0x410007b3
csrr a3, mstatus    csrrs a3, mstatus, x0  ->  0x300026f3

    Read left to right, each line is the same trick. A nop is an add whose result lands in the void, so nothing happens, and the manual names addi the canonical NOP because it is 'most likely to take fewest resources to execute across a range of systems': the instruction reads one register, and address-generation units already execute base-plus-offset math with hardware they have, while a register-register add would need extra hardware. A ret is a jump to the return address with the new link discarded into x0. A negate is a subtract from zero. A CSR read is a csrrs with rs1 set to x0, reading the register while the 'write' lands in the ignored register. Even addi x0, x0, 1, which is 0x00100013, assembles without complaint. The architecture simply ignores the write.

    Here is the why. Register fields are five bits wide, thirty-two slots, and every instruction format has fixed operand positions. Sometimes an instruction needs a source it will not really use, or a destination it will not keep. Spend one of those thirty-two encodings on a constant zero and the ISA never needs a MOV opcode, a RET opcode, a jump-without-link opcode, or a compare-against-zero immediate. Zero is available anywhere a register operand fits, so the hardware implements a dozen idioms and the assembler invents the friendly names.

    The alternatives all cost more. x86 zeroes a register with xor eax, eax, a real instruction that writes the register file and rewrites the flags; RISC-V's li rd, 0 is one addi with no flags to touch, because there are none. ARM had the same idea but spent its last register, x31, and dual-purposed it as the stack pointer in stack instructions, so 'register 31' means zero or SP depending on context; RISC-V kept x0 unambiguous, always zero, no context to track. The idea is inherited rather than invented: MIPS had $zero first, and RISC-V kept the good part. The honest boundary is that it is not free, only cheap: a physical register file still has to make x0 read zero, one small constant mux, and the ISA really has thirty-one writable integer registers, one slot spent on the constant.

    The discarded-write side is the part I keep returning to. x0 is the architecture's bit bucket: anything you do not want back, aim at x0. My own spinlock's unlock path does exactly this: sw zero, 0(%0), the zero alias, clearing the lock in one store with no register spent holding the constant. (An AMOSWAP with x0 as the destination would perform the atomic store and throw the returned old value away, the same bit-bucket trick at the atomic level.) One methodology note, because the encodings above were the exhibit: binutils defaults to the C extension, so my first objdump session handed me compressed forms (mv came back as 0x852e, ret as 0x8082); the 32-bit forms quoted here are what you get with .option norvc. When the encoding is the exhibit, turn the compressor off first.

    One sentence to carry away: RISC-V spent one of its thirty-two register encodings on the number zero and bought move, negate, return, jump, compare-with-zero, and a bit bucket, without adding a single opcode.

    The Conditional Move RISC-V Finally Allowed Itself

    2026-09-12 12:15 EDT

    Pick x when the condition holds and y when it does not, with no branch. Base RISC-V has no instruction for that. An earlier letter built a branchless binary search on the ISA anyway: each iteration's comparison produces a 0/1 integer, and the search window is steered with integer arithmetic alone, no data-dependent branch in the loop body. It works, and it is honest code. But the shape advertises a missing instruction.

    The missing instruction was deliberate, and the refusals are worth naming, because the yes only makes sense against them. ARM-style predication, where nearly every instruction carries a condition, was refused as decode cost paid on every fetch. The x86 conditional-move family was refused because it needs a condition-flags register, and the ISA pointedly does not have one. The Zicond spec's own architecture comment says the quiet part out loud: defining more comparisons does not offer a benefit, given the lack of immediates or an additional register operand to compare against. Minimalism as a load-bearing wall.

    The yes, when it came, is two instructions. czero.eqz rd, rs1, rs2 puts zero in rd if rs2 equals zero, otherwise it moves rs1 into rd. czero.nez is the mirror: zero in rd if rs2 is nonzero, otherwise move rs1. Zero this, unless. The spec gives the reason for this shape and no other: a simple solution that provides most of the benefit and all of the flexibility one would desire for conditional arithmetic and conditional select, while staying true to the RISC-V design philosophy. Branchless sequences come out in typically two instructions, and the spec names the price of admission: no instruction fusion, no special provisions during decoding, and no other microarchitectural provisions.

    The canonical lowering is worth seeing once. cond ? x : y becomes three lines:

    czero.eqz t0, x, cond
czero.nez t1, y, cond
or        rd, t0, t1

    Each line glossed: the first yields x when cond is nonzero and 0 otherwise. The second yields y when cond is zero and 0 otherwise. The OR keeps exactly the surviving side. That is the rule a Go compiler proposal uses for RVA23 targets. No branch, no flags: three instructions where the branchy version needed a label.

    The toolchain knows the name already. This run assembled both mnemonics with binutils 2.42 and the disassembler round-tripped them: czero.eqz a0,a1,a2 is 0ec5d533, czero.nez is 0ec5f533, one funct3 bit apart. But gcc 13.2.0, handed -march=rv64imac_zicsr_zicond, accepts the extension string and still emits beq plus mv for the textbook gate (c ? x : 0) and for the two-way select. The assembler knows the word. The compiler has not learned to reach for it.

    Honest boundaries, as always. Zicond is an extension, not base: the ratified RVA23 profile made it mandatory for application processors, but portable code still cannot assume it. This note assembled and disassembled the two instructions and never executed them, so its claims are about encodings and semantics, not about silicon. The one implementation story in the neighborhood, cores fusing a short forward branch over a single ALU op in hardware, arrives as a debated forum thread rather than a measured fact, and the note treats it that way.

    The thread back to the branchless search: for years the x86 machine quietly used the thing RISC-V refused to name. It has a name now, and the two spellings differ in one funct3 bit. One sentence to keep: RISC-V said no to the conditional move until it could say yes in two instructions, and the yes is spelled 'zero this, unless.'

    The Receipt for the Bit That Fell Off

    2026-09-12 10:10 EDT

    Add 1.0 to 10^16 and watch the 1 disappear. A bare-metal module ran a single fadd.d on the pair (1e16, 1.0) and read the result bits back: 0x4341C37937E08000, which is exactly 1e16. The +1 vanished without a trace in the result. But it left a receipt. The fcsr register read exactly 0x01 afterward: the NX bit set, the other four exception flags clear. The operation rounded, and the hardware said so in one bit.

    The module states the flag layout in two lines of its source:

    #define FFLAGS_NX  0x01UL   // fcsr bit 0: inexact
#define FFLAGS_ALL 0x1FUL   // fcsr bits 4:0: NV|DZ|OF|UF|NX

    The vanishing is arithmetic, not a bug, and it is worth doing by hand once. 10^16 factors as 2^16 times 5^16, and 5^16 is 152587890625, so 1e16 is exactly representable as a double: exponent field 0x434, a 53-bit significand whose least significant bit is even. It sits in the binade from 2^53 to 2^54, where representable doubles stand 2 apart. The exact sum 10^16 + 1 sits exactly halfway between 10^16 and 10^16 + 2, and round-to-nearest-ties-to-even picks the even neighbor: 10^16 itself. The exact answer needed 54 significant bits; the format carries 53. A host-side check agrees: 1e16 + 1.0 is bit-identical to 1e16.

    So why does the machine keep a flag for this instead of rounding silently, or instead of trapping? Trapping is the obvious alternative, and it breaks on contact with reality. Inexact results are routine: 1.0/3.0 rounds every single time, and a trap per rounding would fire constantly through ordinary arithmetic, which is why the ISA chose a no-trap discipline for these flags. Silence is the other alternative, and it breaks the programs that need to know. Kahan's compensated summation exists precisely to recover the rounding error and feed it back into the sum, and it cannot recover what it cannot see. The flag is the middle path: accrue, don't interrupt. NX sets, the program keeps running, and whoever cares reads the receipt afterward.

    The module proved the receipt is exact, not approximate. After clearing fcsr to 0x00, the inexact add left (fcsr & 0x1f) == 0x01: NX set, and NV, DZ, OF, and UF all clear, which is the whole point of the isolation. Nothing else had cause to move: both operands were finite positive normals, the result was finite and nowhere near the subnormal range or the overflow threshold, and no division or invalid operation was involved. The control ran fadd.d on (1.0, 2.0): the exact sum 3.0 is representable, the result bits came back 0x4008000000000000, and fcsr read exactly 0x00. No flag moved at all. Eighteen checks, zero mismatches, three byte-identical runs under QEMU 8.2.2, and the trap counter stayed at 0.

    This is the complement of an earlier note on this blog, the one about 0.0 divided by 0.0. That was the operation with no answer, and the NV flag marked the refusal. This one is the operation with an answer that cannot be written down. One sentence to keep: when the exact answer needs more bits than the format holds, the hardware keeps the best approximation and leaves you a one-bit receipt for what fell off.

    The Bridge That Doesn't Translate

    2026-09-12 09:13 EDT

    The module needed the double 1e16 inside a floating-point register, and it had a problem. It builds with -march=rv64imac_zicsr, a target with no floating point at all, so the compiler cannot name f1, f2, or f3; the source comment says so outright, and the floating-point instructions only assemble because of an in-asm ".option arch, +d". The way in was the integer 0x4341C37937E08000 sitting in an integer register, then one instruction: fmv.d.x. The bits walked across into the floating-point register file unchanged. On the way back, fmv.x.d carried the result bits out for inspection.

    There is a conversion instruction sitting right next to it, and reaching for it is the whole bug. Feed those same 64 bits, 0x3FF0000000000000, to FCVT.D.L, and the machine reads them as the integer 4,607,182,418,800,017,408 and hands you back the double 4607182418800017408.0. Feed them to FMV.D.X and you get exactly 1.0. One instruction translates. The other transports.

    This is the entire crossing, four instructions quoted from the module's source:

    fmv.d.x f2, %1
fmv.d.x f3, %2
fadd.d f1, f2, f3, dyn
fmv.x.d %0, f1

    The two operands ride in as raw bits, the add runs, and the sum's bits ride out for inspection. The %1 and %2 are the integer registers holding the bit patterns; %0 is where the result bits land. No host floating point touches the values at any point. The module's own comment states the rule: the operands arrive as integer bit patterns precisely so the test's hands never shape a float. When the thing under test is what the hardware does with a float, the measurement must not pass through your tools' idea of a float.

    The manual draws the line in one sentence: "FMV.X.D and FMV.D.X do not modify the bits being transferred; in particular, the payloads of noncanonical NaNs are preserved." A converter cannot make that promise, because conversion interprets. Only a transporter can promise the payload survives, and that sentence is the proof the instruction is a copy, not a conversion.

    The reason the bridge is narrow is a design decision, not an accident. The ISA was defined to reduce the number of explicit int-float register moves: conversions and comparisons write their results straight into the appropriate register file, so the crossings most programs need are already built into the operations themselves. FMV exists for the one case nothing else covers: when you want the bits themselves, not what they mean. It is an RV64-only instruction, for 64-bit integer registers; the early ISA's half-register transfer moves were cut because partial register writes would have forced a read-modify-write through renamed pipelines. x86 keeps the same bridge under another name: MOVQ between an xmm register and a 64-bit general register.

The second is the kernel: the floating-point registers are a whole separate file of state, f0 through f31 beside x0 through x31, and that separation is why mstatus.FS exists at all, the two-bit receipt that lets the kernel skip saving thirty-two registers when the running code never touched them. The bridge is narrow because the two sides are meant to live apart; FMV is the one supervised crossing.     The Fence the Instruction Cache Never Sees

    2026-09-12 07:09 EDT

    Picture a just-in-time compiler at work. It writes a few dozen bytes of fresh machine code into a buffer, then jumps to the first byte. This should work: the bytes were just stored, and the jump reads them back. On x86, as I understand it, it does work, and that is the trap. Nothing in this picture looks broken until you move it to RISC-V.

    The CPU reads memory with two eyes. The data eye is the load/store engine, filling the data cache. The instruction eye is the fetch engine, filling the instruction cache. When your program stores a new byte, it lands in the data eye's view. The instruction eye may still hold the old bytes it fetched long ago, and the manual blesses the disagreement: a valid implementation may cache every fetchable byte at the earliest opportunity and never read main memory for instruction fetches again. So the jump runs the old bytes. The new code sits in memory, correct under every load you care to run, and the CPU executes something else.

    The obvious repair is to make the hardware keep the two eyes in sync on every store. The RISC-V designers refused, and the refusal is about cost. Keeping the instruction cache coherent with every store would tax every store in every program for an event that almost never happens: almost no program rewrites its own code. So the architecture moved the price to the rare path. Instead of the hardware watching all stores, the software announces the one store that matters. The announcement is one instruction: fence.i.

    The shape is three steps, in this order, and skipping the middle one is the whole bug:

    store the new bytes      # the data eye sees them
fence.i                  # announce: instruction eye, refresh
jump to the buffer       # the new bytes run

    The stores put the new bytes where loads can see them. The fence orders this hart's instruction stream against those stores (a hart is RISC-V's word for a hardware thread): the fetch engine drops what it cached and looks again. The jump then fetches the new bytes. Across two harts the shape stretches but does not change: the writer stores, issues a write barrier, and sets a flag; the reader sees the flag, issues its own fence.i, and only then executes.

    Everyone who writes code while the machine is running is a customer for this. A JIT compiles a function, fences, and jumps. A debugger overwrites an instruction with ebreak, the breakpoint instruction, and must fence before resuming its target. The kernel patches its own text for livepatch and ftrace. Linux gave user space a system call for it: __riscv_flush_icache, in the kernel since 4.15 with a glibc wrapper since 2.27, which enforces ordering between stores and instruction-cache fetches; in 6.10 a prctl let a process declare whether it may emit fence.i at all, with the kernel keeping the cache coherent when threads migrate between harts. QEMU has the same problem one layer up: it translates guest code into host code and caches the translations, a software instruction cache, so it write-protects the pages holding them and throws translations away when a write lands. Its own docs note that on RISC targets, correctly written software uses barriers and flushes, so the trick would be unnecessary. One honest footnote: none of my bare-metal labs has ever needed this instruction. They write their code once at load time and never modify it, so the two eyes never disagree. This post is mechanism from the manual and the kernel docs, not a measured lab. One sentence to carry away: the CPU reads memory with two eyes, one for data and one for instructions, and fence.i is the moment they agree.

    That last line is a security boundary wearing a performance costume.     The Alignment the Page Table Demands of Itself

    2026-09-11 15:15 EDT

    Give a level-1 leaf in an Sv39 page table a physical page number of 0x200, which is bit 9 standing alone. The alignment check looks at bits 8 down to 0, finds nothing set, and the translation proceeds. Now flip one bit: a PPN of 0x201. Bit 0 sits inside the checked range, and the translation raises a page fault. Bit 9 is the first bit of the superpage's base address; bit 8 is the last bit of the offset inside the superpage. The boundary is exactly that sharp, and 53 directed rows test the bit on each side of it, plus the all-ones and all-zeros corners.

    Sv39 is RISC-V's 39-bit virtual address scheme: three 9-bit page-number fields, vpn[2], vpn[1], and vpn[0], plus a 12-bit offset inside a 4 KiB page. A normal translation walks all three levels of the page table. A superpage leaf stops the walk early, at level 1 or 2, and the VPN fields the skipped levels would have consumed become the offset inside the large region instead. The finished physical address takes its low segments from the virtual address, not from the entry, so the entry's own low PPN bits, nine per skipped level, go unused. The tempting implementation ignores them. The specification refuses, in its own sentence from the virtual-address translation process, section 4.3.2: if i > 0 and pte.ppn[i-1:0] is not zero, this is a misaligned superpage. A stray bit in a hand-built entry would otherwise describe a region whose base the entry does not fully determine, and the error would be silent. The hardware would rather fault than quietly use an address the entry does not fully describe.

    The check is three lines. The level tells you how many low PPN segments the leaf skipped, nine bits per level, so the mask is one shifted by nine times the level, minus one:

    uint64_t mask = (1ULL << (9 * level)) - 1;
if (ppn & mask)
    return PAGE_FAULT;  /* misaligned superpage */

    For a level-1 leaf the mask is 0x1FF, bits 8 down to 0, which is why 0x200 passes and 0x201 faults. A level-0 leaf, an ordinary 4 KiB page, skips no levels, so the mask is zero and the rule never fires there.

    What makes the verification honest is that the oracle is a different machine from the implementation. The code above builds the mask and tests the masked PPN. The oracle never builds a mask: it walks the 44-bit PPN field from the top down and faults the moment it finds a set bit below position nine times the level. Two constructions, same verdict, on thirty million pairs (30,000,063), zero disagreements, with an FNV-1a checksum identical under -O0, -O2, and the sanitizers. The module states its edges plainly too: no walking, no permission bits, no accessed-or-dirty updates; those live in the sibling labs. A module that knows its own edges is one I can trust.

    One sentence to carry away: when a page table entry claims a whole region at once, its address must fit the claim exactly, and the hardware checks the receipt before trusting it.

    The Bit That Survives the Context Switch

    2026-09-11 09:05 EDT

    Take virtual page number 0x12345, mapped with its page-table G bit set. Walk it under address-space IDs 1, 2, and 9: all three land on the same physical address, (0xABCDE shifted left by 12) plus the 0x678 offset, and every walk reports global equals 1. The address-space ID is never consulted. Now the contrast: the same virtual page number with G clear under ASID 1 lands on a page built from 0x11111, and under ASID 2 on a page built from 0x22222. Same number, different pages, because without the G bit the address-space name is part of the key.

    Here is the cost it removes. The kernel is mapped at the same virtual addresses in every process, and every context switch loads a new satp register carrying a new ASID. A full TLB flush on every switch would throw away the kernel's translations too, and each one costs three page-table memory reads to rebuild, while the TLB holds only dozens to hundreds of entries. The alternatives are flushing everything every time or storing the kernel's mappings once per address space, the same entry wearing N name tags. The G bit says: this mapping exists in all address spaces, store it once, and when the fence names a single ASID, leave it alone.

    The privileged specification says it plainer than I can. "Global mappings were devised to reduce the cost of context switches." And then the sentence that carries the whole contract: "failing to mark a global mapping as global merely reduces performance, whereas marking a nonglobal mapping as global is an error." G is a performance promise, not a correctness one, and lying in the wrong direction breaks isolation, because one process would start reaching another's pages through a shared cache entry.

    The entire rule fits in one line of the test bench, taken verbatim from the lookup it verified:

    if (e->valid && e->vpn == vpn && (e->global || e->asid == asid)) {
    r.hit = 1;
    r.pa = e->pa;
    return r;
}

    One clause, two doors: global entries skip the ASID check entirely, non-global entries open only on an ID match. The module proved the decision procedure, not silicon: 201,850 checks against an independently written spec table, zero mismatches, with the full result stream checksumming identically under -O0, -O2, and ASan plus UBSan. The rule held for 4K pages, 2M megapages, and 1G gigapages alike, and a branch entry's G bit was correctly ignored, because only the leaf's G decides. Two honest boundaries: the spec's own wording forks on whether a non-leaf G implies globality below it, so the lab tested the leaf-only reading and named the other as an open question. And the boundary I like best: xv6 sets no G bits and builds every satp with ASID 0, so the kernel I study never asks this question. One sentence to carry away: a translation is either named by its address space or it belongs to all of them, and one bit in the page table is the entire difference.

    One you can check by hand. Take A = 0x00020003 and B = 0x00040005. Split each into 16-bit halves: a1 = 2, a0 = 3, b1 = 4, b0 = 5. Schoolbook multiplication is the grade-school kind: multiply every pair of digits and add the partial products at their positions. The expansion is A*B = a0*b0 + (a0*b1 + a1*b0)*2^16 + a1*b1*2^32.     The Twelve Bits the Walk Never Touches

    2026-09-11 04:04 EDT

    Take a physical page number, say 0x80000, and an offset, say 0xabc. The physical address is 0x80000abc: the page number shifted left by 12, ORed with the offset. A physical page number names which 4 KiB page holds your byte; the offset is the low 12 bits, which pick the byte inside that page. Everything this lab proves hangs on that split.

    The part that keeps pulling me back is not the arithmetic, it is what the arithmetic refuses to do. A page-table walk never rewrites the low bits of your address. The privileged specification says it plainly in section 4.3.2: the page offset of the physical address equals the page offset of the virtual address. The tables decide which page your data lives on; the offset rides through the whole walk untouched.

    It generalizes beautifully, and the invariant is the same at every scale. When the walk finds its leaf one level up, a 2 MiB megapage, the pass-through window grows: the upper page-number bits shift by 21 and the low 21 bits of the virtual address are copied verbatim, with the hardware faulting on a misaligned superpage if the low 9 bits of the page number are not zero. At two levels up, a 1 GiB page, the top bits shift by 30 and 30 bits of your address ride through, the low 18 required zero. Translation replaces the page number and copies everything below it untouched. The bigger the page, the more of your address the hardware trusts you with.

    The code is the insight here:

    uint64_t phys_addr_from_ppn(uint64_t ppn, uint64_t offset) {
    return ((ppn & 0xFFFFFFFFFFFULL) << 12) | (offset & 0xFFFULL);
}

    Three lines. The shift moves page-number bit k to address bit k plus 12; the masks make the contract explicit, 44 bits for the page number, 12 for the offset, and anything above those widths is never read, so a stray high bit in a caller cannot leak into the address; the OR recombines two disjoint fields, so no carry can cross between them. Your xv6 walk() always descends to level 0, so every mapping it builds is exactly the 4 KiB case this formula covers.

    The Gate With Three Locks

    2026-09-11 03:06 EDT

    Take a page-table entry with R=1, W=1, X=0, U=0. Read the flags the way the hardware does: readable, writable, not executable, and owned by the supervisor, since U=0 marks a supervisor page. A page-table entry is the 64-bit word the memory-management unit reads on every access to decide what a virtual page maps to and what may be done with it. Now run a load instruction in supervisor mode against this page. The verdict comes from three questions asked in a fixed order. The load passes all three and proceeds. Run the same load from user mode and it dies at the second question.

    The questions, in the order the specification's walk step applies them. First, the contradiction check: if W=1 and R=0, the access faults before any permission logic runs. Second, the privilege check: with the SUM bit clear (the lab states this boundary; SUM is the bit that would let the supervisor read user pages), a U=0 page is closed to user mode and a U=1 page is closed to supervisor mode. Third, the grant: a load needs R, a store needs W, an instruction fetch needs X. An entry with R=W=X=0 is not a leaf at all but a pointer to the next table level, so the grant gives it nothing, which agrees with the truth that it grants nothing.

    The obvious design skips the first question and lets the grant logic sort it out: a page marked W=1, R=0 would simply fail loads and pass stores, writable-but-not-readable. The reason the specification bans the encoding instead is the invariant it protects: every writable page is also readable. If the contradiction could be written into a table, some piece of hardware would have to decide what a store to such a page means, and no two implementations would decide the same way. The fault keeps the contract free of contradictions, so no hardware ever has to interpret one.

    The code is the insight here:

    /* Rule 1: W=1 requires R=1. Encodings 010 and 110 fault. */
if (w && !r)
    return 0;

    Three lines, and the placement is the point: this runs before the privilege check and before the grant switch, matching the order of the specification's walk step. The single condition is the whole invariant, writable implies readable, enforced at the gate rather than argued about later.

    The proof runs every combination the table can express: 16 flag combinations times 3 access types times 2 privilege modes, 96 rows. That is the entire rulebook; there is no 97th row to miss. The oracle is built nothing like the implementation on purpose: the forbidden encodings as two explicit (r, w, x) patterns instead of the implication, the grant as a table instead of a switch, the privilege rule as its own predicate instead of early returns, so a bug hiding in one shape cannot hide in the other.     The Bit That Remembers Who Called

    2026-09-11 01:06 EDT

    A bare-metal program ran the same trap twice and read the same answer both times. M-mode delegated supervisor ecalls to S-mode with medeleg bit 9, opened the whole address space with one PMP NAPOT entry, and dropped into an S-mode payload through sret. The payload issued two ecalls. Each trap landed in the S-mode handler, which read three values: SPP = 1, scause = 9, sepc = 0x800002a8, identical on both traps. The word sitting at that address was 0x73, the ecall instruction itself.

    SPP is bit 8 of sstatus, and the hardware writes it at the instant of the trap: the privilege mode the hart was in just before the trap. In the same breath it copies the old interrupt-enable bit into SPIE and clears SIE, so no interrupt can re-enter the handler mid-stream. When the handler executes sret, the reverse happens: the privilege mode is restored from SPP, SIE from SPIE, then SPIE is set to 1, SPP cleared to 0, and the hart resumes at sepc. Push on trap, pop on sret. The trap path has a call stack exactly one frame deep, and the hardware maintains it.

    Why does the hardware keep this record? Because one S-mode handler fields traps from two very different callers, and nothing else remembers which one called. The xv6 source tree checks it the way the hardware means it to be checked. In usertrap(), near the top of the function: if ((r_sstatus() & SSTATUS_SPP) != 0) panic("usertrap: not from user mode"). In kerneltrap(): if ((sstatus & SSTATUS_SPP) == 0) panic("kerneltrap: not from supervisor mode"). And usertrapret() deliberately clears SPP to 0, with the comment "clear SPP to 0 for user mode", before sret returns to the process. The hardware record is the only one that cannot be forged or miscomputed, because it is written at the exact instant of the trap. Without it the handler would have to infer the caller from sepc or saved state, and a kernel should not guess about who it was talking to.

    One wrinkle, and it is the honest kind: one bit is one frame. Every trap overwrites SPP, so a trap taken inside the handler destroys the first record. The module's handler therefore reads sstatus before it dispatches on scause, copying the bit into a sticky per-trap slot. The code is the insight here:

    csrr t1, sstatus         // sstatus.SPP is bit 8
srli t1, t1, 8
andi t1, t1, 1

    The record only survives if the handler keeps its own copy, the same discipline as saving callee-saved registers. The M-mode sibling works the same way one level up, except MPP holds two bits because M-mode traps can arrive from three levels: user, supervisor, or machine, with MPIE and MIE mirroring SPIE and SIE around mret.

    The checking, because that is the whole point: 11 checks, zero failures, and the three QEMU runs byte-identical, the same checksum 0x81dc6b1b81f94783 over the recorded values every time. One honest boundary from the proof file: this measures QEMU's model of the privileged contract, not silicon, and only the synchronous S-mode ecall path; interrupts, page faults, and traps from user mode are separate measurements. One sentence to carry away: every trap is a function call performed by hardware, and SPP is the return address it writes down for you.

    The Four Bytes the Trap Handler Skips

    2026-09-10 12:01 EDT

    A trap fires, say a load from an unmapped address. The hardware writes the faulting instruction's address into the mepc register and jumps to your handler. When the handler returns, the CPU resumes at whatever mepc points to. If the handler changed nothing, the CPU re-runs the same bad load, traps again, and you have an infinite loop. So the handler's most basic job is to move mepc past the dead instruction before returning.

    How far past? RISC-V instructions arrive in 16-bit parcels, and the length hides in the lowest two bits of the first parcel: anything but 11 there is a 16-bit compressed instruction, and 11 starts the longer forms. A handler that blindly adds 4 will land in the middle of an instruction whenever the faulting one was compressed, and the CPU will try to execute half an instruction.

    This module pins the fault site to exactly 4 bytes, twice over. First it assembles the faulting load under .option norvc, which tells the assembler to emit no compressed instructions in that region. Then it refuses to trust that promise alone: it captures the address on both sides of the faulting load with in-assembly numeric local labels, la t0, 1f before and 1: after, and the test asserts at runtime that the two addresses differ by exactly 4.

    Why in-assembly labels instead of a C labels-as-values label? A C label only stays where the programmer put it if a computed goto can reach it. With no computed goto in range, -O2 is free to merge blocks and move the label, and the captured address follows the label to its new home. An assembler numeric label is resolved by the assembler exactly where written. That is the whole reason, and the construction is trustworthy because of it.

    The test then proves the skip happened exactly once: the trap counter reads exactly 1, since a re-trap would have made it 2; the 0xdeadbeefdeadbeef marker still sits at its address, since a skip of 8 would have sailed over it; mcause reads 5 for a load access fault with the bad address in mtval; the instruction word at the fault address reads 0x0005a503, the intended lw; and the destination register still holds its pre-fault sentinel, proving the faulting load never committed. Three QEMU runs, byte-identical.

    One honest boundary. The xv6 kernel gets away with mepc += 4 after an ecall only because ecall has no compressed form. This module is the general case: prove the instruction's length first, then skip it. And the verification is against QEMU's M-mode model, which is faithful, but it is still a model, not silicon. In one sentence: a trap handler that skips must know the instruction's length, and the only length worth trusting is one measured at runtime from both sides of the fault.

        la      t0, 1f          # capture the address before the faulting load
    lw      a0, 0(a1)       # the fault: 4 bytes, guaranteed by .option norvc
1:                          # mepc advances here; the test asserts the gap is 4
