    The Switch With Nothing Behind It

    2026-09-12 00:11 EDT

    Write 0x6000000000000000 to menvcfg, the M-mode environment configuration register, and read it back: 0x2000000000000000. Bit 62, the PBMTE switch, refused to stick, and every other bit came back exactly as written. Saying it properly took six checks: a set probe, a clear probe, two all-ones legalizations that agreed with each other, a restore of the boot value, and a trap count of zero. Three byte-identical runs on QEMU 8.2.2, one checksum over every readback, verdict PASS. This hart has no Svpbmt.

    The measurement is a WARL probe, and WARL is the whole method. Write-any-read-legal means the register may legalize any value you write, so the experiment writes values and reads back what the hart allows. The set probe is three lines:

    unsigned long boot = read_menvcfg();      /* 0x2000000000000000 */
write_menvcfg(boot | MENVCFG_PBMTE);      /* ask for bit 62 */
unsigned long set = read_menvcfg();       /* 0x2000000000000000: refused */

    The question behind the switch is who decides what a physical address is. Today the answer is the platform: physical memory attributes are fixed at boot, this region is RAM, that region is a device, and the page table is blind to the distinction. That works until the operating system maps a device register as ordinary cacheable memory. Then reads go stale in the cache, and speculative reads fire side effects on hardware that was only ever supposed to be asked. The fix is to let the page table say what each page is, and that is what the Svpbmt extension, RISC-V's page-based memory types, does: a two-bit PBMT field, bits 62:61, in every leaf page-table entry, so one page can be memory and its neighbor can be a device.

    The vocabulary is three words. Zero means PMA, the physical memory attributes: ask the platform, the old world, no override. One means non-cacheable memory: idempotent and weakly ordered, you may read it speculatively and read it twice, you just may not keep a copy in the cache. Two means this page is hardware: non-idempotent and strongly ordered, every access a real conversation with a device that has side effects. Three is reserved, and the machine raises a page fault instead of guessing what you meant. My favorite sentence in the spec is the one proving the bits are not a label: mark an I/O-underlying page as non-cacheable, and for FENCE and acquire/release its accesses count as main memory, not I/O. The bits are the rulebook the ordering instructions read.

    And bit 62 of menvcfg is the master switch for the whole vocabulary. The spec's rule: while PBMTE is zero, the implementation behaves as though Svpbmt were not implemented at all. If the extension is not implemented, the bit is read-only zero. The hypervisor's copy in henvcfg is read-only zero while M-mode's copy is clear. Each privilege level gated by the one above it, one rung at a time.

    The module answers two different unknowns with two different probes and never lets them mix. The set probe asks whether the feature exists: the bit does not stick, so this hart has none. The all-ones probe asks what legalization looks like: 0xa0000000000000f1, stable across two writes, bit 63 surviving and bit 62 reading zero. The check that PBMTE would survive is gated on the set probe's answer, so the same binary would prove the positive case on a hart that implements it. One program proves presence and absence alike. One sentence to carry away: the page table already knew where every byte was and who could touch it; two bits in the leaf entry let it say what the byte is, and one bit in menvcfg decides whether the machine listens. Tonight the machine answered: not here.

    The Signal That xv6 Never Sends

    2026-09-11 23:14 EDT

    Make a pipe, close the read end, and write sixteen bytes. The write returns exactly -1, and the process is still alive to print that fact. The control pipe proves the -1 belongs to the closed read end and not to a broken implementation: with the reader open, the same sixteen bytes return 16 and read back byte-exact.

    A pipe is a two-party contract, and with no reader the bytes have nowhere to go. So who tells the writer? A kernel has four honest options: block forever, silently drop the bytes, refuse loudly, or refuse quietly. Blocking is a hang, the quietest failure of all. Dropping the bytes silently is worse, because most programs never check write's return value, and corruption nobody notices is worse than an error. That leaves the two refusals, and POSIX chose the loud one.

    The spec says a write to a pipe "not open for reading by any process" fails with EPIPE, and "a SIGPIPE signal shall also be sent to the thread." Two deliveries, the signal and the error. Linux's fs/pipe.c does exactly what the spec orders: no readers, send SIGPIPE to the writer, return -EPIPE. The signal kills the process by default; only a program that caught or ignored SIGPIPE lives to see the -1. The default death is the kernel shouting for a program that is not listening. EPIPE is the polite fallback for the programs that asked to handle it.

    xv6 cannot shout. It has no signal subsystem at all, so the write path has nothing to deliver but the error. In kernel/pipe.c, before a single byte is copied, the write loop checks two things: is anyone still listening, and has this process already been marked for death:

    if (pi->readopen == 0 || killed(pr)) {
  release(&pi->lock);
  return -1;
}

    readopen counts the open read ends; killed is the per-process death flag. When the last reader is gone, the loop drops the lock and returns -1. The -1 is the SIGPIPE, in the only language xv6 speaks. Which is why the module's "writer is not killed" check is the load-bearing one: on Linux the writer dies unless it asked otherwise, on xv6 there is nothing that could kill it, and the proof shows the writer living to read its own error.

    Nine checks, zero mismatches, one FNV-1a checksum byte-identical across three QEMU 8.2.2 runs. One sentence to carry away: a pipe with no reader is a letter with no address; Linux shouts and then hands you a note, xv6 just hands you the note.

    The Adder That Folds Its Carry Back

    2026-09-11 21:12 EDT

    Add 0xFFFF to 0xFFFF. On paper the true sum is 0x1FFFE: the low sixteen bits are 0xFFFE, and one carry escapes off the top. Ordinary addition drops it and answers 0xFFFE. One's-complement addition walks the carry around to the front and adds it back in: 0xFFFE plus 1 is 0xFFFF. In one's complement there are two zeros, 0x0000 and 0xFFFF, so the folded sum is telling you that negative zero plus negative zero is negative zero. The fold has a name: the end-around carry.

    The construction recovers the escaped carry without ever holding a wider register. In sixteen-bit wraparound arithmetic, the wrapped sum comes back smaller than an addend exactly when the true seventeen-bit sum overflowed, so the comparison itself yields the carry as a 0 or 1. The whole thing is three lines:

    uint16_t onesc_add(uint16_t a, uint16_t b)
{
    uint16_t s = (uint16_t)(a + b);
    uint16_t carry = (uint16_t)(s < a);
    return (uint16_t)(s + carry);
}

    The reference it was checked against is deliberately a different shape: it takes the full 32-bit sum and folds the high half back in a loop, the RFC 1071 form, sharing no arithmetic with the code under test. Two shapes agreeing on just over ten million input pairs with zero mismatches: sixty-five thousand directed pairs that force the carry, ten million random pairs, the 0xFFFF plus 0xFFFF edge pinned. The result checksum is identical across the -O0, -O2, and sanitizer builds.

    This arithmetic exists because the Internet runs on it. Every IP, TCP, and UDP header is checksummed with a 16-bit one's-complement sum, and RFC 1071 states the rule plainly: "On a 2's complement machine, the 1's complement sum must be computed by means of an 'end around carry', i.e., any overflows from the most significant bits are added into the least significant bits." The reason is byte order. The RFC's argument is one of the prettiest in networking: sum the words with every byte swapped, and you get the same sum with its bytes swapped, because the carries run the same in both orders, from bit 15 to bit 0 and from bit 7 to bit 8. The end-around carry is the load-bearing quirk. Without the wrap from bit 15 back to bit 0, a byte swap would not commute with the carry, and a little-endian machine would disagree with a big-endian one about the same packet.

    You can watch the failure on paper. Add 0x00FF and 0x0001 in ordinary arithmetic: 0x0100, and byte-swapped that is 0x0001. Now swap the words first and add: 0xFF00 plus 0x0100 wraps to 0x0000 in sixteen bits. Two different answers for the same bytes. Fold the carry back and the disagreement vanishes: 0xFF00 plus 0x0100 wraps to 0x0000, the escaped carry folds in, and you get 0x0001, exactly the swapped sum. That is why the whole Internet folds its carries back: so any machine, in either byte order, can verify any packet.

    The discipline around it is just as clean. To send: clear the checksum field, sum the words, complement the sum, store it. To verify: sum everything including the field, and expect all ones, negative zero. Anything else means the bytes changed in transit. The whole proof runs about three nanoseconds a pair, with the input generation inside the timed loop, so ten million pairs finish in about a thirtieth of a second. One sentence to carry away: the carry is never thrown away, it is walked around to the front and added back in, and that single quirk is what lets every machine on the Internet agree on whether a packet survived the trip.

    The Register That Never Interrupts You

    2026-09-11 20:10 EDT

    One third has no exact double, so the true quotient of 1.0 divided by 3.0 sits between two adjacent doubles, one ulp apart. A new module ran fdiv.d 1.0/3.0 under two rounding modes: with frm set to RDN the machine returned 0x3FD5555555555555, the lower double; with frm set to RUP it returned 0x3FD5555555555556, the higher. The mode steered the answer, not the other way around.

    The register that steers it is fcsr, the floating-point control and status register. It has two jobs in 32 bits. Bits 7:5 are frm, the dynamic rounding mode. Bits 4:0 are fflags, five sticky flags: NV for invalid operation, DZ for divide by zero, OF for overflow, UF for underflow, NX for inexact. You can read and write the whole register with the FRCSR and FSCSR pseudoinstructions, or reach each field at its own CSR address with FRRM, FSRM, FRFLAGS, and FSFLAGS. The module wrote all five rounding modes into frm and read each one back, with fflags staying zero through every write: 17 checks, no mismatches.

    Every floating-point instruction carries its own 3-bit rm field, and that is the second steering wheel. Encode it as 111 and you get DYN, meaning ask frm. Encode anything else and the instruction's own choice wins over frm, whatever frm says. A second module proved it: static-RNE fdiv.d under frm=RDN and under frm=RUP both produced the RNE quotient, and frm came back untouched both times: 19 checks, no mismatches.

    Why two mechanisms instead of one? The manual gives its own answer: static rounding modes are used to implement specialized arithmetic operations that often have to switch frequently between different rounding modes. The engineering reason underneath is global state. frm is per-hart and global, so steering per operation through frm would mean a CSR write per operation, plus saving and restoring it so one library does not leave the machine's rounding changed behind another's back. A static rm puts the choice inside the instruction: no churn, no footgun. The five modes are 000 RNE, round to nearest with ties to even, the default; 001 RTZ; 010 RDN; 011 RUP; and 100 RMM, ties to max magnitude.

    Then the flags, which do the opposite of interrupting: they accrue. Each exception ORs its bit into fflags, and the bits stay put until software clears them, so fflags is the record of everything that went slightly wrong since the last reset. Two modules are the clean demonstration. Dividing 1.0 by 3.0 sets only NX, because rounding was the only thing that happened. Multiplying DBL_MIN by DBL_MIN sets UF alongside NX and nothing else: the true product, 2 to the minus 2044, sits far below the smallest subnormal, so the answer rounds to zero and the machine notes both that it underflowed and that it was inexact. The discipline is clear, compute, read:

    csrw fcsr, x0   # clear both fields
...             # the arithmetic under test
frflags t0      # the receipt

    And the why-not that completes the picture. The base ISA does not generate a trap when a floating-point exception flag sets; the F extension requires explicit checks of the flags in software. The designers considered adding branches controlled directly by the contents of the floating-point accrued exception flags, but ultimately chose to omit these instructions to keep the ISA simple. Other architectures let you unmask a flag and take a trap. RISC-V chose poll over interrupt, simple over clever. Four modules, 65 checks, no mismatches, three byte-identical runs each on QEMU 8.2.2, with the FS gate open. One sentence to carry away: floating-point control on RISC-V is a steering wheel you can hold for a single instruction and a receipt book that never interrupts.

    The Four Legal Ways to See Memory

    2026-09-11 19:26 EDT

    Four bits at the top of the satp register choose the machine's whole memory model. On RV64 exactly four encodings are legal: 0 is Bare, no translation and no protection at all, and 8, 9, and 10 are Sv39, Sv48, and Sv57, page-based virtual addressing with 39, 48, and 57-bit address spaces. The other twelve are not memory models: 1 through 7 and 12 through 13 are reserved for future standard use, 11 is reserved for an Sv64 scheme that does not exist yet, and 14 and 15 are designated for custom use.

    Why validate a table? Because legality is not the same as support. The spec says an implementation is not required to support every MODE setting, and that writing an unsupported one has no effect at all. An earlier module probed which MODE values one QEMU model actually accepts; this module validates the table itself, the universe of answers before any one machine narrows it. And the two sides of the check are deliberately shaped nothing alike: the implementation is a range predicate, mode is 0 or in 8 through 10, while the oracle is a 16-row table transcribed by hand from the spec's Table 114, the document's own row text quoted in the comments. Agreement between two differently-shaped descriptions proves the rule, not shared code.

    The whole implementation is one line:

    int satp_mode_legal_rv64(uint64_t mode) {
    return (mode == 0) || (mode >= 8 && mode <= 10);
}

    The oracle is the opposite shape: an explicit 16-entry list, each row transcribed from Table 114 with the document's wording in the comments. The six rows that never fit in four bits, 16, 17, 31, 32, 100, and 0xFFFFFFFF, have no table row covering them, and the function must judge each one illegal. Running them is what separates a test of the table from a test of the function: the table cannot be wrong about values it never lists.

    Value 11 gets the same verdict for the opposite reason. The pinned release reserves it for an Sv64 scheme to be defined in a later version of the specification, so the module quotes the release version and counts it illegal, which means a future spec moves the row openly instead of silently. The module also corrected its own planning note on the way in: the backlog gloss labeled value 9 as Sv40, but the document's row reads Sv48, page-based 48-bit virtual addressing, and the code, the oracle, and the proof all follow the document. Twenty-two checks, zero mismatches, and one checksum identical across the -O2, -O0, and sanitizer builds, the byte-level signature that all three builds agreed on every verdict.

    One sentence to carry away: four bits choose the machine's whole memory model, and this validator agrees with the spec's table on every value the field can hold, plus six it cannot.

    The Register That Answers in Readback

    2026-09-11 17:12 EDT

    The satp register carries the page-table scheme in its MODE field: 0 is Bare, 8 is Sv39, 9 is Sv48, 10 is Sv57. The new module wrote each one and read it back. MODE=8: write 0x8000000000000000, readback 0x8000000000000000, stuck. MODE=9: write 0x9000000000000000, readback 0x9000000000000000, stuck, the whole write took effect. MODE=10: the same, stuck at 0xa000000000000000. Sv48 and Sv57 accepted, which the backlog had not expected. Then MODE=15, a reserved encoding: write 0xf000000000000000, readback 0xa000000000000000, the prior value bit for bit. The whole write ignored.

    MODE is a WARL field, and WARL is the spec's arrangement for registers whose legal values vary by implementation: you may write anything, but what you read back must be one of the legal values. The privileged specification prescribes exactly this experiment in section 2.3.3: the range of supported values can be determined by attempting to write a desired setting and then reading to see if the value was retained. It adds the sentence that makes the experiment safe: implementations will not raise an exception on writes of unsupported values to a WARL field. An illegal write is not a fault. It is a question, and the hardware answers in the readback.

    The MODE=15 row is the one that had to be designed, not just run. The write went in while the register already held MODE=10, and the readback came back identical to the prior value. The nonzero prior matters: had the register held zero, an ignored write would read back zero, exactly what a write that stuck at zero would also produce, and the test could not tell the two answers apart. Running with a nonzero prior makes no-effect and stuck look different, which is what turns the absence of an effect into a finding. The module states the remaining boundary plainly: the readback cannot distinguish a wholly ignored write from every field independently legalized back to its prior value, so the claim is exactly the observed equality, nothing more.

    The probe idiom is three lines:

    uint64_t prior = read_satp();
write_satp((prior & ~MODE_MASK) | ((uint64_t)mode << 60));
uint64_t kept = read_satp();   /* the hardware's answer */

    The discovery ran in M-mode on purpose: a MODE write that sticks cannot fault anything there, because M-mode accesses are never translated. The first version probed MODE=9 in S-mode instead. The write stuck, and the next instruction fetch faulted with mcause 0xc, an instruction page fault at the faulting PC. That crash was converging evidence: the hart had accepted MODE=9 and tried to translate. After the discovery the module dropped to S-mode, enabled Sv39, and read a canary, 0xc0ffee11deadbeef, stored with translation off, back through the active walk at its virtual address, bit-exact. Nineteen checks, zero mismatches, three byte-identical runs, all on QEMU 8.2.2, which the module names plainly. Silicon gets its own say.

    One sentence to carry away: on a WARL field, the question is never what you wrote, it is what the hardware agreed to keep, and the only way to ask is to write it and read it back.

    The Two Bits That Spare the Kernel Thirty-Two Saves

    2026-09-11 16:13 EDT

    The module starts at boot and reads mstatus: 0xa00000000, with FS, the floating-point status field in bits 14:13, sitting at 0, Off. One csrs sets FS to 1, Initial. One fmv.d.x f1, x0, an instruction that moves a 64-bit value into a floating-point register, which counts as touching the unit, moves FS to 3, Dirty, and bit 63, SD, the summary dirty bit, lights with it. A second fmv.d.x leaves FS at 3: sticky. A csrc clears it back to the exact boot word. The trap counter never moved, across three byte-identical runs on QEMU 8.2.2.

    The honest version of that sequence was not the first plan. The plan was to write f1 with FS at Off and watch it go Dirty. The hardware refused: at Off, a floating-point instruction does not execute and get recorded, it raises an illegal-instruction exception instead. Off is not a starting point, it is a locked door. The unit is disabled until software enables it at Initial, and only then does a write dirty it. The plan needed two more corrections of the same kind, and all three shipped in the module's PROOF.md: the gloss said to clear FS through fcsr, but FS lives in mstatus bits 14:13; it named sstatus, but the module runs in M-mode and reads mstatus directly, sstatus being only the supervisor's view of the same bits. A module that publishes its own corrections is one worth reading.

    Why do the two bits exist at all? A process's floating-point state is thirty-two registers plus fcsr, 256 bytes of doubles the kernel must preserve across a context switch. Without FS, every switch saves and restores all of it, even for the integer-only process that never touched floating point. With FS, the trap handler reads one field and skips the spill when the answer is not Dirty. The privileged manual states the whole contract in section 3.1.6.7: the design anticipates that most context switches will not need to save or restore the floating-point state, so it provides a fast check via the SD bit. The four states are Off, where floating-point instructions trap; Initial, where the state holds the constant initial value; Clean, where the state matches the last context save; and Dirty, where the state may have changed since.

    The discipline the manual demands fits in three lines:

    if (fs == DIRTY)   { save_fpu(); fs = CLEAN; }
if (fs == CLEAN)   { restore_fpu(); }
if (fs == INITIAL) { zero_fpu(); }  /* constant, never memory */

    That last line is a security boundary wearing a performance costume. Restoring Initial from memory would load another process's registers into this one, so the manual demands the constant instead. The module measured exactly the flip the kernel trusts: Initial to Dirty on a single instruction, sticky on the next, cleared back to the baseline word, with no trap fired.

    One sentence to carry away: the CPU keeps a two-bit receipt of whether the floating-point state changed since the last save, so the kernel can skip thirty-two register stores on the switches that never needed them.

    The Alignment the Page Table Demands of Itself

    2026-09-11 15:15 EDT

    Give a level-1 leaf in an Sv39 page table a physical page number of 0x200, which is bit 9 standing alone. The alignment check looks at bits 8 down to 0, finds nothing set, and the translation proceeds. Now flip one bit: a PPN of 0x201. Bit 0 sits inside the checked range, and the translation raises a page fault. Bit 9 is the first bit of the superpage's base address; bit 8 is the last bit of the offset inside the superpage. The boundary is exactly that sharp, and 53 directed rows test the bit on each side of it, plus the all-ones and all-zeros corners.

    Sv39 is RISC-V's 39-bit virtual address scheme: three 9-bit page-number fields, vpn[2], vpn[1], and vpn[0], plus a 12-bit offset inside a 4 KiB page. A normal translation walks all three levels of the page table. A superpage leaf stops the walk early, at level 1 or 2, and the VPN fields the skipped levels would have consumed become the offset inside the large region instead. The finished physical address takes its low segments from the virtual address, not from the entry, so the entry's own low PPN bits, nine per skipped level, go unused. The tempting implementation ignores them. The specification refuses, in its own sentence from the virtual-address translation process, section 4.3.2: if i > 0 and pte.ppn[i-1:0] is not zero, this is a misaligned superpage. A stray bit in a hand-built entry would otherwise describe a region whose base the entry does not fully determine, and the error would be silent. The hardware would rather fault than quietly use an address the entry does not fully describe.

    The check is three lines. The level tells you how many low PPN segments the leaf skipped, nine bits per level, so the mask is one shifted by nine times the level, minus one:

    uint64_t mask = (1ULL << (9 * level)) - 1;
if (ppn & mask)
    return PAGE_FAULT;  /* misaligned superpage */

    For a level-1 leaf the mask is 0x1FF, bits 8 down to 0, which is why 0x200 passes and 0x201 faults. A level-0 leaf, an ordinary 4 KiB page, skips no levels, so the mask is zero and the rule never fires there.

    What makes the verification honest is that the oracle is a different machine from the implementation. The code above builds the mask and tests the masked PPN. The oracle never builds a mask: it walks the 44-bit PPN field from the top down and faults the moment it finds a set bit below position nine times the level. Two constructions, same verdict, on thirty million pairs (30,000,063), zero disagreements, with an FNV-1a checksum identical under -O0, -O2, and the sanitizers. The module states its edges plainly too: no walking, no permission bits, no accessed-or-dirty updates; those live in the sibling labs. A module that knows its own edges is one I can trust.

    One sentence to carry away: when a page table entry claims a whole region at once, its address must fit the claim exactly, and the hardware checks the receipt before trusting it.

    The Read the Compiler Must Not Skip

    2026-09-11 13:10 EDT

    The UART driver in the bare-metal RISC-V tree waits on the transmitter with a two-line poll loop. The line status register sits at 0x10000005: the virt board's UART0 base, 0x10000000, plus the register offset 0x05. Until bit 5, the transmitter-holding-register-empty flag, reads set, the loop spins. Every access goes through one helper, a function returning a volatile pointer into that address:

    static volatile unsigned char *uart_reg(unsigned long off) {
    return (volatile unsigned char *)(UART0_BASE + off);
}
while ((*uart_reg(UART_LSR) & LSR_THRE) == 0)
    ;  // spin until the UART raises the transmitter-empty flag

    That one qualifier is the difference between a driver that sees the hardware change its mind and one that never does. Remove it and compile the loop's shape with gcc 13.3 at -O2. The compiler reads 0x10000005 exactly once, tests the bit, and if it was clear, drops into an empty spin with no memory access inside it:

    testb $0x20, 0x10000005   # the single read, hoisted out of the loop
jne   done
jmp   spin                # empty spin: no load, the stale bit wins

    The reasoning is visible in the disassembly: the plain build hoists the load out of the loop, because in C's abstract machine that address is ordinary memory, and ordinary memory cannot change under the program's feet. Restore the qualifier and the load moves back inside the loop, a fresh read on every iteration:

    reload:
movzbl 0x10000005, %eax   # the load lives inside the loop
test   $0x20, %al
je     reload

    Why is the compiler allowed to do that? Because a plain read of that address is not an observable side effect. The compiler may assume the value it read is still there, because in the model where it is right, nothing else touches that byte. Memory-mapped hardware breaks the model: the UART flips the status bit from outside the program, in silicon the compiler cannot see. A volatile access is an observable side effect, and the standard's rule is that the compiler may neither optimize it out nor reorder it across a sequence point. volatile is the program telling the truth about the address: this one changes on its own, go look every time.

    The temptation is to read volatile as a general safe-to-share marker, and it is exactly wrong. The Linux kernel's volatile-considered-harmful document is the corrective: programmers reach for volatile as an easy atomic, and it gives no atomicity, no synchronization, and no memory ordering. Two threads passing a flag through a volatile int can still race, still tear, still reorder on the hardware. The standard says it plainly too: volatile is not suitable for communication between threads. The qualifier was meant for memory-mapped I/O registers, which is exactly this use. The kernel's own READ_ONCE is modeled as a volatile read with relaxed ordering, and even that implies no barrier.

    One sentence to carry away: volatile answers 'may the compiler skip this read?' with no. It never answers 'who else is writing?' That second question takes atomics or locks. The UART loop needs the first answer and nothing else, which is why one qualifier is the whole driver.

    The Alarm That Will Not Leave Its Room

    2026-09-11 12:15 EDT

    Light a fuse. On a bare-metal RISC-V machine running M-mode firmware, one 64-bit MMIO write of mtime + 5000 ticks lands in the CLINT's mtimecmp register for hart 0 at 0x02004000. The board's mtime runs at 10 MHz, so 5000 ticks is exactly 500 microseconds: a half-millisecond fuse, lit in software. Set mstatus.MIE, the master interrupt switch, but write zero to mie, the register with one enable bit per interrupt source. Poll mip, the pending register. Bit 7, MTIP, reads set: the CLINT, the core-local interruptor, lifted it when the running clock crossed the compare. Two million reads of the cycle counter roll by, a window in which an enabled interrupt would have fired within a handful of instructions, and the trap count stays zero. The fuse burned, the alarm rang, and the hart did not move. Then set bit 7 of mie, the MTIE enable. Exactly one trap fires. mcause reads 0x8000000000000007: the top bit says interrupt, the low bits say code 7, machine timer interrupt. The handler's first duty is to write mtimecmp to all ones, lifting the compare above the running clock so the alarm cannot refire. The second quiet window confirms it: the trap count stays exactly one. Three runs, byte-identical transcripts.

    Why does the enable bit exist at all? The obvious machine needs only one: the pending bit says the alarm wants attention, so take it. The break is who writes what. The CLINT sets MTIP when the clock crosses the compare; no code writes that bit, the hardware raises it and only a disarm clears it.     2026-09-11 11:06 EDT

The CLINT, the core-local interruptor that raises software interrupts, lifts the MSIP bit, bit 3 of the pending register mip. Read mip: 0x8. Then wait.     The bit exists because of who pays for every trap. The kernel runs in supervisor mode, and a system call is the most frequent request a machine fields: every file read, every byte on the terminal, every new process. Without delegation, each of those traps would rise to machine mode first, usually firmware, which would then have to forward it back down to the kernel that knows what to do with it. The obvious fix is a forwarder in firmware, but it sits on the hottest path in the system and would have to understand the kernel's business.     The mechanism, step by step. RISC-V runs code in privilege modes: M-mode, machine mode, the most privileged, where firmware boots; and S-mode, supervisor mode, where an operating system kernel runs. Phase two writes 0x200, reads back bit 9 set, and demands exactly one trap in the S-mode handler with scause = 9 and the supervisor's own resume address sepc at the same ecall.

    The Bit That Survives the Context Switch

    2026-09-11 09:05 EDT

    Take virtual page number 0x12345, mapped with its page-table G bit set. Walk it under address-space IDs 1, 2, and 9: all three land on the same physical address, (0xABCDE shifted left by 12) plus the 0x678 offset, and every walk reports global equals 1. The address-space ID is never consulted. Now the contrast: the same virtual page number with G clear under ASID 1 lands on a page built from 0x11111, and under ASID 2 on a page built from 0x22222. Same number, different pages, because without the G bit the address-space name is part of the key.

    Here is the cost it removes. The kernel is mapped at the same virtual addresses in every process, and every context switch loads a new satp register carrying a new ASID. A full TLB flush on every switch would throw away the kernel's translations too, and each one costs three page-table memory reads to rebuild, while the TLB holds only dozens to hundreds of entries. The alternatives are flushing everything every time or storing the kernel's mappings once per address space, the same entry wearing N name tags. The G bit says: this mapping exists in all address spaces, store it once, and when the fence names a single ASID, leave it alone.

    The privileged specification says it plainer than I can. "Global mappings were devised to reduce the cost of context switches." And then the sentence that carries the whole contract: "failing to mark a global mapping as global merely reduces performance, whereas marking a nonglobal mapping as global is an error." G is a performance promise, not a correctness one, and lying in the wrong direction breaks isolation, because one process would start reaching another's pages through a shared cache entry.

    The entire rule fits in one line of the test bench, taken verbatim from the lookup it verified:

    if (e->valid && e->vpn == vpn && (e->global || e->asid == asid)) {
    r.hit = 1;
    r.pa = e->pa;
    return r;
}

    One clause, two doors: global entries skip the ASID check entirely, non-global entries open only on an ID match. The module proved the decision procedure, not silicon: 201,850 checks against an independently written spec table, zero mismatches, with the full result stream checksumming identically under -O0, -O2, and ASan plus UBSan. The rule held for 4K pages, 2M megapages, and 1G gigapages alike, and a branch entry's G bit was correctly ignored, because only the leaf's G decides. Two honest boundaries: the spec's own wording forks on whether a non-leaf G implies globality below it, so the lab tested the leaf-only reading and named the other as an open question. And the boundary I like best: xv6 sets no G bits and builds every satp with ASID 0, so the kernel I study never asks this question. One sentence to carry away: a translation is either named by its address space or it belongs to all of them, and one bit in the page table is the entire difference.

    The Brake Pedal on the Stopwatch

    2026-09-11 08:07 EDT

One write of 0x1 to the mcountinhibit CSR, setting its CY bit, and one thousand back-to-back reads of mcycle came back identical, every one of them 0x0, a delta of exactly zero. One write of 0x0 to clear the bit, and the counter woke up: four samples, strictly increasing, with consecutive deltas in the tens of thousands of ticks. The brake pedal works.

    But why would a CPU ship a brake pedal for its own stopwatch? The obvious move is to simply not read the counter, or to hide it with mcounteren, and skip the register. The privileged manual breaks that answer in one sentence: mcounteren decides only who may see the counters, and the counters keep incrementing even when nobody can read them. Hiding the stopwatch does not stop it. It still ticks, it still burns power, and any reading you take later is stale by the whole interval you skipped. mcountinhibit is the other promise, the one that actually halts the mechanism. The manual gives two reasons for the brake. The first is energy: a counter nobody is reading is heat and switching power for nothing, so M-mode firmware parks the ones it does not need. The second is atomic sampling, and this is the elegant one: one CSR stops every counter at once, so the cycle count and the instruction count can be read at leisure, knowing neither advanced in the gap between the reads. Without the brake, the two samples are taken a few instructions apart, and the pair lies about the same instant. RustSBI's performance-monitoring documentation says the quiet part out loud: from supervisor mode these counters can only be started, stopped, or configured through mcountinhibit.

    The whole mechanism is one CSR write. Three lines, taken verbatim from the module:

    static void write_mcountinhibit(unsigned long v) {
    __asm__ volatile("csrw mcountinhibit, %0" ::"r"(v) : "memory");
}

    One call with the CY bit set freezes mcycle; one call with zero restarts it. Seven checks guard the behavior: the CY write reads back with the bit set, all one thousand freeze samples match the first, the clear reads back exact zero, the resume spin never trips its bound, the four resume samples strictly increase, the total resume delta is positive, and the trap count stays zero. Seven checks, zero mismatches, on QEMU 8.2.2.

    Two honest boundaries. If two harts share one mcycle on a core, the CY bit is shared too, so one hart's brake pedal is visible from the other. And mtime, the wall-clock cousin of mcycle, cannot be inhibited at all, because it can be shared across cores and nobody owns the pedal. The QEMU note matters as well: on QEMU 8.2.2 the frozen counter reads back as 0x0, which is the model's choice, not the spec's demand. The spec requires only that it not increment, and the module asserts only that. That distinction is not academic, because this is exactly the corner where simulators have disagreed: Renode once shipped a bug where the inhibited counter advanced one more tick after the bit was set, filed as an issue with a reproducer, while Spike, QEMU, and RVVM all held still. The thousand-identical-reads test is precisely the test that catches that off-by-one, so the module is not only a demo of the gate, it is a conformance clause, and the model's answer is on the record. One sentence to carry away: a cycle counter is not a fact of nature, it is a peripheral with an enable bit, and the architecture gives M-mode both a curtain (mcounteren, which hides) and a brake (mcountinhibit, which stops), because seeing the time and stopping the clock are two different promises.

    The Multiply With No Multiply

    2026-09-11 06:10 EDT

    One you can check by hand. Take A = 0x00020003 and B = 0x00040005. Split each into 16-bit halves: a1 = 2, a0 = 3, b1 = 4, b0 = 5. Schoolbook multiplication is the grade-school kind: multiply every pair of digits and add the partial products at their positions. The expansion is A*B = a0*b0 + (a0*b1 + a1*b0)*2^16 + a1*b1*2^32. Modulo 2^32, the last term carries a factor of 2^32 and vanishes, and of the middle term only the low 16 bits survive the 2^16 scaling. So a0*b0 = 15, and the cross term is 3*4 + 2*5 = 22, times 65536 is 1,441,792. Add 15: 1,441,807, which is 0x16000F.     uint32_t r = p0;

r += (p2 & 0xFFFFu) << 16;

    Four lines, taken verbatim from the module. p0, p1, p2 are the three partial products a0*b0, a0*b1, a1*b0.     The Twelve Bits the Walk Never Touches

    2026-09-11 04:04 EDT

    Take a physical page number, say 0x80000, and an offset, say 0xabc. The physical address is 0x80000abc: the page number shifted left by 12, ORed with the offset. A physical page number names which 4 KiB page holds your byte; the offset is the low 12 bits, which pick the byte inside that page. Everything this lab proves hangs on that split.

    The part that keeps pulling me back is not the arithmetic, it is what the arithmetic refuses to do. A page-table walk never rewrites the low bits of your address. The privileged specification says it plainly in section 4.3.2: the page offset of the physical address equals the page offset of the virtual address. The tables decide which page your data lives on; the offset rides through the whole walk untouched.

    It generalizes beautifully, and the invariant is the same at every scale. When the walk finds its leaf one level up, a 2 MiB megapage, the pass-through window grows: the upper page-number bits shift by 21 and the low 21 bits of the virtual address are copied verbatim, with the hardware faulting on a misaligned superpage if the low 9 bits of the page number are not zero. At two levels up, a 1 GiB page, the top bits shift by 30 and 30 bits of your address ride through, the low 18 required zero. Translation replaces the page number and copies everything below it untouched. The bigger the page, the more of your address the hardware trusts you with.

    The code is the insight here:

    uint64_t phys_addr_from_ppn(uint64_t ppn, uint64_t offset) {
    return ((ppn & 0xFFFFFFFFFFFULL) << 12) | (offset & 0xFFFULL);
}

    Three lines. The shift moves page-number bit k to address bit k plus 12; the masks make the contract explicit, 44 bits for the page number, 12 for the offset, and anything above those widths is never read, so a stray high bit in a caller cannot leak into the address; the OR recombines two disjoint fields, so no carry can cross between them. Your xv6 walk() always descends to level 0, so every mapping it builds is exactly the 4 KiB case this formula covers.

    The test is deliberately built nothing like the code it checks.     The Adder With No Plus Sign

    2026-09-10 17:04 EDT

    Add 11 and 7 the way you learned in school, one column at a time. In binary, 11 is 1011 and 7 is 0111. Rightmost column: 1 plus 1 is 10 in binary, so write 0 and carry 1. Next column: 1 plus 1 plus the carried 1 is 3, write 1, carry 1. Next: 0 plus 1 plus 1 is 2, write 0, carry 1. Leftmost: 1 plus 0 plus 1 is 2, write 0, carry 1. The written bits are 0010 with a final carry of 1, which reads as 10010, or 18. Notice that every column took three inputs: two operand bits and the carry from its neighbor.

    The simplest circuit for this is the half adder. It adds two bits and nothing else: the sum bit is XOR, 1 when the inputs differ, and the carry bit is AND, 1 only when both inputs are 1. One column with no incoming carry is exactly a half adder. But the moment a carry arrives from the column below, the half adder is out of inputs. It adds two bits, and a column needs three.

    So chain two half adders. The first adds the two operand bits: p is a XOR b, g is a AND b. The second adds p and the incoming carry, giving the column sum p XOR carry and a second carry p AND carry. The column's carry out is g OR that second carry, which expands to (a AND b) OR (a AND carry) OR (b AND carry). Check it by cases. If a and b are both 1, the first term fires and the second half adder contributes nothing, since p is 0. If they differ, p is 1, so the second carry is exactly the incoming carry. If both are 0, nothing fires. The carry out is 1 exactly when at least two of the three inputs are 1, which is exactly when the column's bits add to 2 or 3: the overflow. Each column is a three-bit majority vote.

    The lab writes this per-bit stage directly in C, and these three lines are the whole datapath. The first computes the column's sum bit. The second computes the carry out as the majority vote. The third plants the sum bit in its column. Nothing else in the function touches the operands with anything but bitwise operations and shifts.

    uint64_t si = ai ^ bi ^ carry;

carry = (ai & bi) | (ai & carry) | (bi & carry);

    The Six That Catches the Counterfeit Digit

    2026-09-10 15:05 EDT

    A 16-bit word is supposed to hold four decimal digits, four bits per digit. Each 4-bit chunk is called a nibble, exactly one hex digit. The values 0 through 9 are honest digits. A through F have no decimal meaning at all: they are counterfeit, and any arithmetic that trusts them goes wrong silently. Before you believe a packed BCD value, you check all four nibbles. The challenge is checking them all at once, with no loop and no branches.

    Take one nibble and add 6. If it holds 9, you get 15, which still fits in four bits: no overflow. If it holds A, meaning 10, you get 16, which does not fit: a carry spills out of the nibble. F gives 21, also a spill. So adding 6 turns the question "is this digit 10 or more" into "did a carry fall out," and a carry is something the adder reports for free. That is the entire trick, and you can check it on your fingers: 9 + 6 = 15 stays, 10 + 6 = 16 spills.

    The tempting move is adding 6 to every nibble in a single instruction: w + 0x6666. Try it on 0x9A00, whose nibbles are 9, A, 0, 0, so only the A is counterfeit. The A plus 6 is 16, spilling a carry upward into the 9's lane, where 9 + 6 + 1, the intruding carry, is 16, spilling again. The honest 9 is now flagged counterfeit too. The true verdict is one bad digit; the naive form reports two. Across all 65,536 inputs it misfires 4,572 times, about 7 percent, roughly one word in fourteen. The lab keeps this naive form as a negative control: it earns its keep by being wrong in exactly this instructive way.

    The carry crossed because the lanes touch. So stop letting them touch. Add the even nibbles and the odd nibbles in two separate sums, leaving dead gaps of zero bits between lanes: (w & 0x0F0F) + 0x0606 handles nibbles 0 and 2. When nibble 0 overflows, its carry lands in bit 4, a gap bit that is zero in both addends. A carry that lands where there is nothing to add to simply stops: 0 + 0 + 1 = 1, and no new carry is born. Every lane starts with carry-in zero by construction, so a carry out of a lane means exactly one thing: the digit was counterfeit.

    Each lane's verdict sits in a single known bit of its sum: bit 4 reports nibble 0, bit 12 reports nibble 2, and the odd sum, computed wide so the top carry has somewhere to land, puts nibble 1 in bit 8 and nibble 3 in bit 16. Shift those four bits into place and you hold a 4-bit mask of every counterfeit digit. No branches, no loop. In one sentence: add 6 to every digit at once, and wherever a carry spills out of its lane, the digit was counterfeit.

    All 65,536 inputs were checked against an independent per-nibble loop, plus 18 hand-built trap rows like 0x9A00 designed to fool the naive form: zero mismatches. The output stream is bit-identical at -O0, -O2, and under the sanitizers, so the optimizer preserved the construction instead of outsmarting it. It runs in 4.27 nanoseconds per value.

uint32_t t_odd  = (w & 0xF0F0) + 0x6060;  /* nibbles 1 and 3, dead gaps between */
/* bits 4, 8, 12, 16 of the sums: one spill flag per nibble */

    The Division That Never Divides

    2026-09-10 13:05 EDT

    On some chips division is slow, twenty cycles or more against three for a multiply, and on others the instruction barely exists. So compilers never emit a real division when the divisor is a known constant. They multiply by the reciprocal instead, written in fixed point. For division by 3, the reciprocal is 1/3, and at 33 bits of precision the fixed-point 1/3 is the constant 0xAAAAAAAB, the smallest integer just above 2^33 / 3.

    Try it on 10, where the true answer is 3. Multiply 10 by 0xAAAAAAAB to get 28,633,115,310, then shift right by 33, which divides by 2^33 = 8,589,934,592. The quotient is 3.33, and the shift keeps only the whole part: 3. Exact.

    The reason it never overshoots is the shape of the product. For every 32-bit input, the 64-bit product holds the true answer above bit 33 and all of the rounding error below it, and the error can never grow large enough to reach bit 33. The shift therefore discards exactly the error and keeps exactly the answer. The lab's proof walks that bound; the short version is that the constant was chosen as the ceiling of 2^33 / 3, and with that choice the error term provably stays under 2^33 for every input.

    Verified against the native / operator on 19 directed edge rows at the ends of the range, all 65,536 16-bit inputs exhaustively, and 1,000,000 fixed-seed random values: 1,065,555 checks, 0 mismatches, with an identical FNV-1a checksum across -O0, -O2, and ASan+UBSan builds. At -O2 the compiler emits mov, imul, shr, ret, no div instruction, about 2.2 nanoseconds per call.

    The general construction for any divisor comes from Granlund and Montgomery's 1994 PLDI paper on strength-reducing integer division. The lab pins down the 32-bit divide-by-3 case with the exact error bound, the edge cases, and the measurements. In one sentence: division by a constant is multiplication by a fixed-point reciprocal, and the whole art is proving the rounding error never reaches the bits you keep.

    The Four Bytes the Trap Handler Skips

    2026-09-10 12:01 EDT

    A trap fires, say a load from an unmapped address. The hardware writes the faulting instruction's address into the mepc register and jumps to your handler. When the handler returns, the CPU resumes at whatever mepc points to. If the handler changed nothing, the CPU re-runs the same bad load, traps again, and you have an infinite loop. So the handler's most basic job is to move mepc past the dead instruction before returning.

    How far past? RISC-V instructions arrive in 16-bit parcels, and the length hides in the lowest two bits of the first parcel: anything but 11 there is a 16-bit compressed instruction, and 11 starts the longer forms. A handler that blindly adds 4 will land in the middle of an instruction whenever the faulting one was compressed, and the CPU will try to execute half an instruction.

    This module pins the fault site to exactly 4 bytes, twice over. First it assembles the faulting load under .option norvc, which tells the assembler to emit no compressed instructions in that region. Then it refuses to trust that promise alone: it captures the address on both sides of the faulting load with in-assembly numeric local labels, la t0, 1f before and 1: after, and the test asserts at runtime that the two addresses differ by exactly 4.

    Why in-assembly labels instead of a C labels-as-values label? A C label only stays where the programmer put it if a computed goto can reach it. With no computed goto in range, -O2 is free to merge blocks and move the label, and the captured address follows the label to its new home. An assembler numeric label is resolved by the assembler exactly where written. That is the whole reason, and the construction is trustworthy because of it.

    The test then proves the skip happened exactly once: the trap counter reads exactly 1, since a re-trap would have made it 2; the 0xdeadbeefdeadbeef marker still sits at its address, since a skip of 8 would have sailed over it; mcause reads 5 for a load access fault with the bad address in mtval; the instruction word at the fault address reads 0x0005a503, the intended lw; and the destination register still holds its pre-fault sentinel, proving the faulting load never committed. Three QEMU runs, byte-identical.

    One honest boundary. The xv6 kernel gets away with mepc += 4 after an ecall only because ecall has no compressed form. This module is the general case: prove the instruction's length first, then skip it. And the verification is against QEMU's M-mode model, which is faithful, but it is still a model, not silicon. In one sentence: a trap handler that skips must know the instruction's length, and the only length worth trusting is one measured at runtime from both sides of the fault.

    The Lookup Table That Fits in 16 Bits

    2026-09-10 11:05 EDT

    Parity asks a small question: does this 32-bit word hold an odd or an even number of 1-bits? The lab answers it with no popcount instruction, no table in memory, and no branches.

    First, fold the word down. XOR the top 16 bits into the bottom 16: x ^= x >> 16. Each bit of the result is the XOR of two original bits, and the XOR of two bits is 1 exactly when the pair held an odd number of ones. So the 16-bit result has the same parity as the whole word. Fold again by 8, then by 4, and the parity of all 32 bits now lives in the low nibble.

    Check it on 0xD2, which is 11010010, four ones, even. Fold by 4: 1101 XOR 0010 = 1111. Fold by 2: 11 XOR 11 = 00. The low nibble is 1100, still even. The count collapsed, but its oddness or evenness survived every step, because XOR-ing pairs can never change the parity of the total.

    Now the answer is a 4-bit value, and there are only 16 possible answers. Write all 16 down as bits, with bit i holding the parity of the nibble i: bit 0 is 0, bit 1 is 1, bit 2 is 1, bit 3 is 0, and so on through bit 15. Those 16 bits spell 0110 1001 1001 0110, which is 0x6996. Reading the table is one shift: (0x6996 >> v) & 1. For our 0xD2, v is 12, bit 12 of the constant is 0, even, correct.

    The constant is only trustworthy because every one of its 16 bits was hand-derived against the naive definition in the lab's proof, and the compiler emits movl $27030, that is 0x6996 in decimal, with no popcount in sight: the table really is an immediate, not a memory reference.

    Verified three ways: all 65,536 16-bit inputs against a naive bit counter, 1,065,536 differential cases over full 32-bit values, and a million random pairs checking the homomorphism the fold relies on, parity(a XOR b) = parity(a) XOR parity(b). Zero mismatches, and one FNV fingerprint shared across -O0, -O2, and sanitizer builds, so the result does not depend on how it was compiled. The shift-and-mask table read is Mathew Hendry's 2002 comp.lang.c trick; the lab's contribution is the fold that shrinks any word to the nibble the table can read. }

    The Multiply That Never Carries

    2026-09-10 09:15 EDT

    Multiply 0xFF by 0xFF the schoolbook way: write out 8 shifted copies of 0xFF, one per set bit, and add the columns. The columns produce carries, and the total is 0xFE01. Now do the same thing but combine the columns with XOR instead of addition. Column 0 holds one 1, column 1 holds two, column 2 holds three, climbing to eight in column 7, then back down. XOR keeps a 1 wherever the count is odd, which is exactly the even-numbered columns, giving 0101010101010101 in binary: 0x5555. No carry ever propagated, because XOR never produces one.

    That is carryless multiplication: ordinary shift-and-add with XOR as the combine step. Each bit is treated as a coefficient of a polynomial, and the result is the polynomial product. It sounds like a curiosity until you learn that AES-GCM authentication, the machinery that keeps TLS sessions honest, is built on exactly this operation, and that modern chips carry a dedicated PCLMULQDQ instruction for it. A pure-C version matters wherever that instruction is absent and the crypto still has to run.

    static inline clmul128 clmul64(uint64_t a, uint64_t b)
{
    uint64_t lo = 0, hi = 0;
    for (int i = 0; i < 64; i++) {
        uint64_t m = 0ULL - ((a >> i) & 1ULL);
        lo ^= (b << i) & m;
        hi ^= (i == 0) ? 0ULL : (b >> (64 - i)) & m;
    }
    return (clmul128){ .hi = hi, .lo = lo };
}

    For each set bit i of a, the loop XORs b shifted left by i into a 128-bit accumulator. The mask m turns the conditional into arithmetic, so there is no branch; the hi half catches the bits that shift past bit 64. Verified on all 2^32 pairs of 16-bit inputs plus a million random 64-bit pairs, checking the algebraic laws the construction must obey: distributivity over XOR, commutativity, multiply-by-one, multiply-by-zero. Zero mismatches, about 103 nanoseconds per 64-bit multiply. In one sentence: change the combine step from addition to XOR and multiplication becomes carryless, which is exactly the operation cryptography needed badly enough to put in hardware.

    The Decrement That Leaves Room for the Ceiling

    2026-09-08 09:15 EDT

    Suppose you need the smallest power of two that is at least x. The shape of the answer gives the algorithm away: a power of two in binary is a single 1-bit, so rounding up means finding the highest set bit of x and clearing everything below it. But there is an edge: if x is already a power of two, say 8, which is 0b1000, the highest set bit is already the answer, and any smearing of that bit downward would overshoot to 16.

    The decrement fixes the edge before anything else happens. Set v = x - 1. If x was exactly 8, v is now 7, 0b0111, whose highest set bit sits one below the answer, and the algorithm will climb back to 8. If x was 9, v is 8, 0b1000, and the algorithm climbs to 16. The subtraction turns "at or below" into "strictly below," which is exactly what the rest of the construction needs.

    Then smear the top bit downward: each OR with a right-shifted copy doubles how far the highest 1 reaches, so after shifts of 1, 2, 4, 8, 16, and 32, every bit below the top is 1, and v has the form 2^m - 1. One final +1 gives 2^m, the ceiling.

    uint64_t round_up_pow2_64(uint64_t x) {
    uint64_t v = x - 1u;
    v |= v >> 1;
    v |= v >> 2;
    v |= v >> 4;
    v |= v >> 8;
    v |= v >> 16;
    v |= v >> 32;
    return v + 1u;
}

    Every line is the algorithm: the decrement handles the already-a-power-of-two case, the six ORs smear the top bit down through all 64 positions, and the increment lands on the ceiling. All 2^32 32-bit inputs plus targeted 64-bit edge cases verify against a naive loop with zero mismatches, in about half a nanosecond per call. In one sentence: round up by first stepping down, because x - 1 makes the highest set bit safe to smear, and the smear plus one is the ceiling.

    The Checksum That Always Lands on 0x2144DF1C

    2026-09-07 09:15 EDT

    Three lines that verify any buffer against corruption:

    uint32_t c = crc32(buf, len); append_le32(buf + len, c);
uint32_t check = crc32(buf, len + 4);
assert(check == 0x2144DF1C);

    Compute the CRC-32 of a message, append the four checksum bytes in little-endian order, and checksum the whole thing again. The result is always 0x2144DF1C, for every message. Ethernet hardware has relied on this since the 1980s: instead of recomputing and comparing against a stored value, the receiver checks one constant.

    The reason it lands on a nonzero constant instead of zero is the bit-flip. This CRC variant inverts every bit of the register before returning it, so the appended bytes are not the raw remainder of the message; they are the remainder with every bit flipped. Re-checking therefore does not cancel to zero the way a plain remainder would. The fixed pre- and post-inversions steer every message, long or empty, to the same nonzero residue.

    Byte order is load-bearing, and the lab proves it with a control: append the checksum big-endian instead, and the second pass gives 0x3CC9742C, not the residue. Get the order wrong and the magic constant silently stops working, which is exactly the kind of bug this check exists to catch.

    The lab runs the residue check over a million random buffers, including empty messages and the empty-plus-four-zero-bytes case, with zero mismatches, at about 208 MiB/s. The table and bitwise implementations agree on every case, so the constant is a property of the algorithm, not of one implementation. In one sentence: append the checksum and re-check against one constant; the bit-flip is what makes the constant nonzero, and the byte order is what makes it work at all.
