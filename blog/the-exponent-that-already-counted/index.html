The obvious program is a loop: start at bit 63, walk down, stop at the first 1, count the steps. It works, and for x = 2^63 it finishes after a single test. But for x = 1 it inspects 63 zeros first. The running time depends on the answer, and that is the whole problem: one branch per bit, mispredicted on random data, and a timing channel that leaks the input's magnitude. A quick check on this machine: the loop takes about 81 nanoseconds per value on inputs under 256, and about 4 when the top bit is set. About twenty times slower, decided by the input, while the float version below takes about 5 to 7 nanoseconds on both.

This lab rebuilds a hardware operation in portable C. Chips count leading zeros as a single hardware operation: x86 calls it LZCNT, ARM calls it CLZ, RISC-V's Zbb has one. Inside, that operation is a priority encoder, not a loop but a mesh of gates that examines all 64 bits at once, in space rather than time, the answer falling out of the wiring as the signal propagates. The lab uses no builtins and no intrinsics, so it cannot call that operation. Instead it borrows a top-bit finder every CPU is guaranteed to have: the float conversion unit. Leading zeros are 63 minus floor(log2(x)), so the real question is what power of two x sits under, and every conversion of an integer to a double must compute that exponent to normalize the value, storing floor(log2) plus a bias of 1023 in bits 62 through 52. The cast does the counting for free. So the trick is never to count at all: reshape x until the question you need is exactly the question the cast already answered, then read the exponent field.

Take x = 5, binary 101. Smear the top set bit downward with x |= x >> k for k = 1, 2, 4, 8, 16, 32. The first step turns 101 into 111, each step doubles how far the run of ones reaches, and after all six every bit at or below the top set bit is 1, so the filled value is exactly 2^(n+1) - 1 where n is the top bit's position. Cast that to double and the conversion computes exponent n, stored as n + 1023. Read bits 62 through 52 through a union, subtract the bias, and you have n; 63 minus n is the leading-zero count, 61 for 5. Nothing was counted. The exponent the cast already computed was read back out.

The whole implementation, for reference:

bits = double_bits((double)x);
n = ((bits >> 52) & 0x7FFu) - 1023u;
if (x >> 53)
    n -= 1;
return 63 - n;

That read is exact only while the filled value converts exactly. Past 2^53, neighboring doubles sit more than 1 apart, so the cast rounds. From n = 54 up it always rounds up to 2^(n+1), a distance of 1 against at least 3 the other way, and the exponent reads one too high. The knife edge is n = 53: 2^54 - 1 is the exact midpoint between 2^54 - 2 and 2^54, and round-ties-to-even picks 2^54, whose significand 1.0 has an even least bit against 1.111...1's odd one. So the field reads one too high exactly when x >> 53 is nonzero, and the correction is one line: subtract 1 in that case. That is what the third line of the code above is for.

Re-deriving the tie fixed the correction, and the rerun is clean: 10,065,537 checks, about ten million, zero mismatches, one checksum byte-identical across the -O0, -O2, and sanitizer builds, no sanitizer reports. The oracle is __builtin_clzll on every one of the 65,536 sixteen-bit inputs, x = 0 pinned to 64 by contract, and ten million fixed-seed random 64-bit values, roughly half of them exercising the rounding correction. Best of five benchmark reps: 14.292 nanoseconds a value, about 70 million a second. One sentence to carry away: never count what the hardware already counted; reshape the question until the cast's exponent is the answer.
